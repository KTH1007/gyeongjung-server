# 과부하 방어 (rate limiting과 연결 제한)

요청이 몰리거나 자원이 가득 찰 때, 앱과 DB에 닿기 전에 앞에서 거절해서 서버를 지킨다. 알림이 왔을 때의 대응은 `docs/runbook.md`에 있고, 이 문서는 설정이 왜 이 값인지와 바꾸는 방법을 적는다.

## 구조
1. **Cloudflare** (앞단): 이상 트래픽을 막는다. 도메인과 함께 #39에서 설정한다.
2. **nginx**: 쓰기 요청 속도를 IP별로 제한하고(`429`), 동시에 처리 중인 요청 수를 제한한다(`503`).
3. **앱과 DB**: DB 연결 풀이 가득 차면 3초 안에 실패시키고, api의 Tomcat 스레드와 대기열을 제한하며(계획 2), 호스트 메모리가 부족하면 알린다.

## nginx 한도
서버 `.env`에서 환경변수로 바꾼다. 비워 두면 기본값이다.

| 환경변수 | 기본값 | 의미 | 넘으면 |
|---|---|---|---|
| `LIMIT_WRITE_RATE` | 5 | IP당 초당 쓰기 요청 수 | `429` + `Retry-After: 1` |
| `LIMIT_WRITE_BURST` | 20 | 순간적으로 더 받아 주는 쓰기 요청 수 | `429` |
| `LIMIT_CONN_PER_IP` | 30 | IP당 동시에 처리 중인 요청 수 | `503` |
| `LIMIT_CONN_TOTAL` | 400 | 서버 전체 동시에 처리 중인 요청 수 | `503` |

- **대상**: 속도 제한은 `POST`, `PUT`, `PATCH`, `DELETE`만 센다. 읽기 요청은 속도 제한을 받지 않는다. 동시 연결 제한은 `/healthz`를 뺀 모든 요청에 걸어서 읽기도 센다. 메서드와 상관없이 서버가 동시에 감당할 양을 지키는 장치이고, 이 서비스는 읽기가 대부분이라 읽기를 빼면 서버 전체 한도가 의미 없어지기 때문이다. `/healthz`는 둘 다 받지 않는다.
- **방식**: nginx `limit_req`의 leaky bucket이다. 처음 한 건과 burst만큼은 바로 통과시키고(`nodelay`), 그 뒤로는 초당 `LIMIT_WRITE_RATE`건만 통과한다. 고정 윈도우의 경계 문제가 없다.
- **키**: Cloudflare 뒤의 실제 방문자 IP(`CF-Connecting-IP`, Cloudflare 대역에서 온 연결만 믿는다).
- **상태 저장**: IP별 상태를 공유 메모리에 둔다(`write_per_ip`, `conn_per_ip` 각 10m). nginx 문서 기준 IP 약 16만 개 분량이다. 서로 다른 IP 5만 개가 쓰기 요청을 보낸 뒤 nginx 컨테이너 메모리가 4.8MiB에서 10.9MiB로 늘었다(IP당 약 120바이트, 두 영역 합). 컨테이너 한도는 64MiB다. 영역이 가득 찼을 때의 동작은 시험하지 않았다.
- **응답**: 공통 오류 형식(`application/problem+json`, `code`)과 `X-Request-ID`가 붙는다. `429`의 `code`는 `TOO_MANY_REQUESTS`, `503`은 `SERVICE_UNAVAILABLE`이다. 거절은 접근 로그에 `429`/`503`으로 남기고 오류 로그에는 쏟아내지 않는다. `503`은 api가 직접 줄 수도 있어서, 같은 접근 로그 줄의 `upstream=`이 `-`이면 nginx가 api를 부르지 않고 거절한 것이고 주소가 있으면 api가 준 것이다.

### 수치의 근거
- 사용자는 약 10명이고 쓰기 요청(구독 등록, 피드백)은 사람당 드물다. 초당 5건에 burst 20은 정상 사용을 한참 넘는 값이다. 이동통신 공유 IP에 여러 명이 묶이는 경우도 있어서 IP당 한도는 넉넉하게 잡았다.
- `LIMIT_CONN_TOTAL`은 Tomcat의 `max-connections`(400)와 같다. api가 하나만 남아도 전체 한도를 혼자 받아야, 거절을 Tomcat의 연결 끊김이 아니라 nginx가 공통 오류 형식으로 먼저 한다. 이 관계는 `TomcatOverloadSettingsIT`가 지킨다.
- **이 값들은 측정한 값이 아니라 안전한 시작값이다.** 계획 2의 실제 엔드포인트와 #15의 24시간 수집에서 지표를 보고 조정한다.

### 바꾸는 법
1. 서버 `.env`의 값을 고친다.
2. `docker compose up -d nginx`로 컨테이너를 다시 만든다. 한도는 컨테이너가 시작할 때 설정 템플릿(`ops/nginx/templates/default.conf.template`)에 채워지므로 `nginx -s reload`로는 반영되지 않는다.
3. 값이 숫자가 아니면 nginx가 시작하지 못한다. 한도 없이 조용히 뜨지 않게 하려는 것이다.

시험은 `ops/nginx/test/verify.sh`의 [9]~[11]이다 (한도, 응답 형식, 기본값, 잘못된 값).

## 앱과 DB
### DB 연결 풀
| 설정 | 값 | 환경변수 (compose의 worker) |
|---|---|---|
| 최대 크기 | 5 | `DB_POOL_MAX_SIZE` |
| 연결 대기 시간 | 3초 | `DB_CONNECTION_TIMEOUT_MS` (밀리초) |
| 최소 유휴 | 정하지 않음 (최대와 같은 고정 크기) | |

- **왜 3초인가**: 기본값(대기 30초)이면 DB가 느려질 때 요청이 30초씩 쌓여 스레드가 묶인다. 가득 차면 3초 안에 실패시킨다.
- **왜 5인가**: HikariCP 공식의 계산(코어 수 × 2 + 디스크 수)을 2코어에 적용한 값이다. 실측한 값이 아니다. 서울 API 호출 예산(하루 950건)을 하루에 균등하게 나누면 약 90초에 한 번이라(폴링 일정은 #9에서 확정) worker가 DB를 동시에 쓰는 작업은 1~2개뿐일 것으로 본다.
- 기본값은 `application.yml`에 있어서 worker, 나중에 생길 api, IDE 실행, 시험이 모두 같은 값을 쓴다. compose에서 넘기는 변수는 worker 서비스만 있다. 스프링의 환경변수 규칙(`SPRING_DATASOURCE_HIKARI_*`)으로 컨테이너마다 다르게 줄 수 있다.
- **확인한 것**: worker 컨테이너를 환경변수 없이 띄우면 `hikaricp_connections_max`가 5이고, `DB_POOL_MAX_SIZE=3`이면 3이다. 풀 1개에 연결을 점유하고 한 번 더 요청하면 3.27초 만에 실패한다(`ConnectionPoolExhaustionIT`).
- **연결 수 합**: 풀은 프로세스(컨테이너)마다 따로 있다. 전체 연결 수는 `프로세스 수 × 풀 크기`의 합이고 MySQL `max_connections`(기본 151) 이하여야 한다. 예: worker 5 + api 2개 × 5 = 15.
- **#9에서 재확인**: `GET_LOCK` 전용 연결이 풀에서 1개를 계속 점유하면 작업에 쓸 수 있는 연결은 4개다.

### Tomcat (api용 자리)
| 설정 | 값 | 의미 |
|---|---|---|
| `server.tomcat.threads.max` | 50 | 동시에 처리하는 요청 수 (스프링 기본 200) |
| `server.tomcat.accept-count` | 50 | 스레드가 모두 찼을 때 줄 세우는 연결 수 |
| `server.tomcat.max-connections` | 400 | 동시에 받는 연결 수 (nginx 전체 한도와 같다) |

worker는 웹 포트를 닫아 두어서(`server.port: -1`) 지금은 효과가 없다. api가 생기면 같은 `application.yml`로 적용된다. 값은 측정 전 제안이고 계획 2의 api 이슈에서 확정한다. 스프링의 환경변수 규칙으로 덮어쓸 수 있다(예: `SERVER_TOMCAT_THREADS_MAX`).

### 호스트 메모리 알림
`host-memory-low`: 서버 전체의 가용 메모리가 10% 미만으로 5분 이어지면 알린다(`ops/grafana/alerting/rules.yml`). 값이 없으면 "측정할 수 없습니다"로 요약한다. 규칙은 모두 7개이고 `ops/smoke.sh`는 호출하는 쪽이 넘기는 `EXPECTED_ALERT_RULES`(7)와 비교한다. 이 숫자는 배포 파이프라인(#14)이 넘긴다. 대응은 `docs/runbook.md`에 있다.

## Redis를 쓰지 않는 이유와 도입 조건
- 지금은 입구 nginx가 하나라서 api가 몇 개든 요청이 nginx를 먼저 지나고, 한도가 합쳐서 계산된다. Redis는 컨테이너와 장애점이 늘고, 기본 nginx는 Redis와 연동할 수 없어 다른 빌드(OpenResty)나 앱 코드가 필요하다. 지금은 얻는 것이 없다.
- 앱 안의 메모리 기반 제한(Bucket4j 등)은 api가 2개가 되면 인스턴스마다 따로 세어 한도가 늘어나서 쓰지 않는다 (설계 9.2).
- **도입을 검토할 조건**: 아래 중 하나가 생기고, Cloudflare의 제한이나 같은 IP를 같은 서버로 보내는 설정으로 풀리지 않을 때다.
  1. 입구 nginx가 2개 이상이 되어 한도를 합쳐서 세야 한다.
  2. 사용자나 기기별 한도가 필요하다 (IP로는 부정확하다).
- 그때도 nginx 제한은 1층으로 남기고 Redis는 2층으로 더한다.

## api를 만들 때 확인할 것
api는 계획 2에서 1개로 시작하고 2개로 늘리는 시점은 따로 정한다.

**처음 만들 때 (계획 2 api 이슈의 완료 조건으로 옮긴다)**
- 앱 로그 파일 방식 결정: 복제본별 파일 이름 또는 표준 출력만. 같은 볼륨의 같은 파일을 JVM 두 개가 쓰면 충돌할 수 있다.
- Prometheus가 `api` 서비스 이름 하나로 복제본을 모두 수집하는 구성 (DNS 기반 탐색)
- 알림 규칙(`jvm-heap-high`, `process-restarted`, `hikari-pool-high`)의 `job` 범위에 api 추가
- api 서비스 설정: 메모리 한도, DB 풀 크기, JVM 옵션, 헬스체크, 재시작 정책
- 폴링과 배치와 서울 API 어댑터가 `app.role=worker`에서만 빈이 되는지 api 역할 컨텍스트로 시험

**2개로 늘릴 때 (그때 이슈 하나를 만든다)**
- 두 복제본의 `up`이 모두 1인지, 로그가 복제본별로 나뉘는지
- DB 연결 수 합이 `max_connections` 이하이고 컨테이너 메모리 한도 합이 서버 메모리 이하인지 (#40 점검)
- 컨테이너 3개가 동시에 기동할 때 Flyway가 한 번만 적용되는지 실측
- 복제본 하나를 멈춰도 요청이 성공하는지, 상태 API의 메모리 캐시가 인스턴스마다 몇 초 다른지 측정

## 아직 확인하지 않은 것
- 한도와 풀 크기, Tomcat 값은 측정 전 시작값이다.
- nginx 공유 메모리 영역이 가득 찼을 때의 동작은 시험하지 않았다.
- 한도의 키가 IP 주소 하나라서, 주소를 계속 바꿔 보낼 수 있는 클라이언트(IPv6 등)는 우회할 수 있다. 1층 Cloudflare가 보완하며 시험하지 않았다.
- nginx를 여러 대로 늘리면 각자 따로 센다.
- 호스트 메모리 알림은 임계를 올린 사본으로 발화와 요약을 확인했고, 실제로 메모리가 10% 아래로 내려가는 상황은 만들지 않았다.
